## Issues

1. **Stale k3s `HelmChart` `kube-system/coredns`** (chart 1.24.1, `bootstrap: true`, created 2024-10-13 by the Ansible bootstrap; the manifest file is no longer in `server/manifests`). The 1.28 helm-controller re-created its install Job `helm-install-coredns`, whose pod is **Pending**: it needs a control-plane node and enterprise is cordoned. If it ever ran, it would `helm upgrade` release `coredns` with chart 1.24.1 over Flux's HelmRelease (chart 1.49.0, release revisions v7/v8). Not touched. It stays harmless while enterprise is cordoned, but it will be recreated at every server hop. Fix it before hop 2 (🔒): delete the `HelmChart` CR without its uninstall finalizer running against Flux's release (check `helmcharts.cattle.io` finalizer behaviour first), or leave it and accept the Pending pod.
2. **kube-vip static pod was recreated** by the new kubelet (new container 17:26:46). The restart counter reads 0 because it is a new pod. The VIP gap fell inside the API restart window, so it added no outage. Expect this at every server hop; compare `startedAt`, not `restartCount`.
3. **Leader-election restarts** from the 28 s API outage, all Running afterwards: cilium-operator 3→4, pgo 2→3, csi-nfs-controller (+1 on 3 containers), metrics-server 7→8, birdweather-ingester 15→16, node-feature-discovery-worker on ziti 4→6 and nova 9→11.
4. **ingress-nginx has 1 replica**, not 2 as the plan assumes (§4.3, §9). It runs on nova; its Ready condition went false during nova's kubelet gap and came back at 17:30:48. Expect a gap of a few seconds with no ready ingress endpoint each time nova restarts. The `Succeeded` controller pod on ziti is a leftover from 2026-10-23.
5. **SUC starts the next agent's Job before it uncordons the previous node.** ziti's Job completed at 17:30:07 and nova's Job started then, while ziti was uncordoned only by 17:30:17. nova was cordoned at 17:30:20–17:30:33, after its `prepare` step, so the two workers were never cordoned at the same time. The margin is only the `prepare` step's duration. If both were cordoned, running pods would keep running, but nothing new could be scheduled for a few seconds.
6. Three `Unknown` upgrade pods (first attempts, killed together with k3s) stay until the SUC Jobs are cleaned up. SUC's retry pod completed each Job. Expected.
